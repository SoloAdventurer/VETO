### D-020 Session-scoped taint closes T14 (2026-10-09) — ACCEPTED
Supersedes the "planned fix" in D-018. Every untrusted observation an agent ingests through VETO taints all of that agent's later actions (`provenance_detail[].via = "ambient"`) for `provenance.session_taint_window_s` (default 900 s, 0 = off) or until an operator resets the agent's context (authenticated and audited in production; the demo harness resets silently at the start of each scripted scenario). Evidence: tests/test_provenance_session.py includes a control run with the feature off, where the hidden-injection export executes, and the same run with it on, where it is blocked.
Cost: over-tainting. A clean-looking action is blocked after the agent has read anything untrusted, until reset or expiry; this is a deliberate availability-for-integrity trade and a thesis measurement (false-block rate vs interception rate, by window size).
Boundary (state it in the thesis): VETO only sees data that enters through registered channels. Data an agent obtains by other routes is invisible; the MCP proxy (D-008) is the planned way to put those routes behind VETO. Decision record schema gains optional `provenance_detail` (schemas/decision.schema.json).

### D-021 Authentication and authorisation; supersedes D-017 (2026-10-10) — ACCEPTED
Every endpoint except `/healthz` and `/v1/auth/info` requires a Bearer API key, checked before request bodies are parsed. Identity comes from the key: an agent key can only act as that agent (body `agent_id` must match, otherwise 403 and an audited `builtin:identity-mismatch` block attributed to the key's real owner), approvals are recorded under the approver's own principal (any `approver_id` in the body is ignored), and containment, context reset, operator observations and the demo endpoints need the operator role. Roles: agent (exclusive, so an agent can never approve, contain or read the audit trail), operator, approver, viewer, admin. Keys are random 256-bit secrets, stored only as SHA-256 hashes, shown once, revocable and rotatable with immediate effect; principal and key changes are written to the audit chain. Policy gains `approvals.max_pending_per_agent` (default 10) so an agent cannot flood the approval queue (T7). Closes the T6 and T7 gaps recorded in D-017.
Remaining limits (state in the thesis): no rate-limiting or lockout of failed sign-ins (failures are counted and shown, not audited, to avoid log flooding), no key expiry, no mTLS or per-key network binding, the bootstrap admin key comes from the environment, and the dashboard keeps the key in sessionStorage (acceptable for a demo, replace with a session cookie for deployment). The compose file ships a demo-only bootstrap key that must be overridden outside a local demo.

### D-022 Approval expiry, rate limits, sign-in lockout, richer anomaly signals (2026-10-11) — ACCEPTED
Closes gaps found in a review of a separate proprietary codebase (Aegis Humanis, Saif's) and in our own D-021 limits. Provenance: only ideas were taken (a held request that expires, per-tenant rate limiting, volume z-score and time-of-day signals). This code was written independently in Python from the behaviours; no source was copied or translated, and that repo is marked proprietary. D-009 stays OPEN: Mohamed and Saif should confirm in writing that ideas from it may be used here.
1. **Approval expiry.** `approvals.expire_after_s` (default 3600, must be > 0). Undecided approvals expire to block: audited with `human_decision = {approver_id: "system", outcome: "expired"}`, never executed, can no longer be approved. This implements what docs/policy-format.md already promised and fixes a real hole: without it, stale approvals held the per-agent cap (D-021) forever and locked an agent out of approvals. Expiry is swept lazily on every propose, approve, list and state call, and rebuilt from the audit log on restart.
2. **Rate limits and lockout.** Token bucket per principal (agents default 300/min burst 60, people 1200/min burst 240) and a lockout of a client address after 10 bad keys in 60 s for 300 s. A valid sign-in never resets the failure count, so one valid key cannot be used to shield guesses against others. Throttled requests are counted, not audited, so a flood cannot fill the evidence log. In-memory, so there is no external store whose failure could fail open. Limits: the lockout keys on the TCP peer address (behind a reverse proxy that is the proxy; forwarded headers are not trusted because they can be spoofed), and counters reset on restart.
3. **Anomaly heuristic-0.2.** Adds a per-agent rolling-baseline volume spike (z-score over the agent's own last 30 minutes, needs 5 minutes of history and 5 requests in the current minute) and an optional `anomaly.working_hours` soft signal (declared in policy, off by default, scores 0.35 so it can never flag on its own). Each fired signal adds a plain-language reason stored in the audit record (`anomaly.reasons`, schema updated). Still escalate-only (invariant 2). Cost to measure in the evaluation: the volume signal can flag a long-idle agent that becomes busy.
Not taken: payload encryption in a holding area (our audit must stay readable and verifiable; it holds no payload secrets), per-tenant multi-tenancy, SaaS webhook adapters, Redis, NATS. Its audit "hash chain" hashes each entry against an empty previous hash, so it detects nothing; ours links records and is verified.

### D-023 Restart safety and shadow mode (2026-10-11) — ACCEPTED
**Restart safety.** Before this entry a restart released the kill switch and forgot session taint, operator resets, volume counters and anomaly baselines (all in memory), which contradicted fail-closed (invariant 6). The audit log is now the source of truth and the service replays it on start. To make that possible the log records what it previously did not: every registered observation (`REGISTER_OBSERVATION`: id, source, derived origin, capped flag, time, SHA-256 of the content, never the content), every context reset including the demo harness's (quiet `log-` records instead of silent ones), and each start (`SERVICE_START`). Records are written before the in-memory change they describe. The log is verified on start; if it fails, the service starts in containment and writes `CHAIN_BROKEN`. Containment then lasts until the log is repaired (an operator can release it for the running process only). Evidence: tests/test_restart_safety.py, which fails on the old behaviour in six places.
Cost: startup replays the log, so start time grows with its size (acceptable for SQLite and a demo; the replay window is bounded for counters and baselines but not for observations, containment and resets). Moving the log to a database with indexed queries is the reason to revisit this at the PostgreSQL decision.
**Shadow mode.** `VETO_MODE=shadow` (default `enforce`; any other value refuses to start): the full pipeline runs and the verdict is recorded with `mode: "shadow"`, but the Execution Gateway is never called, nothing is held for approval, and shadow verdicts cannot be approved into execution. Allowed verdicts count toward limits as if the caller had proceeded, so later verdicts match what enforcement would have said. The dashboard shows a banner and "would allow / block / hold" statuses, and the intercepted tally counts only would-blocks. Shadow is chosen at start, recorded in `SERVICE_START`, and there is no API to switch to it, so a compromised operator account cannot quietly turn enforcement off. Invariant 5 is unaffected because shadow mode removes execution rather than adding a path to it.
Not yet built: replaying recorded traffic against a candidate policy to diff decisions (the next step; it needs the trusted-store facts at the time of each request, which are not recorded today).


### D-024 Evaluation harness and first results (2026-10-11) — ACCEPTED
`python3 scripts/run_eval.py` (code in `backend/veto/evaluation/`) generates a seeded, labelled set of cases (default seed 7: 855 cases, 943 scored trials, 663 unsafe in 24 attack classes, 280 legitimate in 7 classes), runs it through the real gateway on a simulated clock, and writes `experiments/results/report.md` and `results.json` (git-ignored). Labels are written in the generator before anything runs. Held requests are decided by an oracle human (approve what is meant to be approved, reject the rest). Configurations: `full`, `no_session_taint`, `no_anomaly`, `provenance_blind`, `rules_only`, plus an analytic `ungoverned` baseline. Metrics: UIR (unsafe actions that did not execute) with Wilson 95% intervals, exact McNemar on paired unsafe trials, false blocks, unnecessary holds, latency percentiles. `tests/test_evaluation.py` fails CI on any false allow in `full` (at a smaller scale), and `run_eval.py` exits non-zero on one.
First results (seed 7): full 100% UIR (99.4-100%), 0 false allows, 0 false blocks. No session taint 84.9%, provenance-blind 74.2%, rules only 84.9%; both drops are significant (McNemar p < 1e-30). Anomaly detection contributed nothing on this set: the `no_anomaly` run matches `full` exactly, because every attack here is stopped by deterministic rules first. That is expected (it can only escalate) but it means this dataset does not yet measure the anomaly model; a stealthy behavioural attack class is needed for that.
What the run found: (1) a harness bug, approved clearance updates leaked between cases and made 5 unlock attempts look like false allows; fixed by restoring the simulated world before every case, not by touching the gateway. (2) A real policy gap: the demo policy had no allow rule for outbound messages, so all 30 legitimate messages were blocked (10.7% false blocks). Added `allow-external-message-allowlisted` (admin role, allowlisted domain, clean context) with a positive case and three negative cases.
Claims discipline (D-013): the same people wrote the attacks and the defences, the set is synthetic, and 100% on it is a regression result, not a security proof. Independent attacks (Saif's suite, T1-T13 mapping) and a larger adaptive adversary are still required before any thesis claim. The `ungoverned` row is an assumption (every well-formed request executes), not a measurement.

### D-025 PostgreSQL audit backend (2026-10-11) — ACCEPTED
The audit log gets a second storage backend behind the same contract (`append`, `all`, `latest_for_request`, `verify`). `VETO_DB=postgresql://...` selects it; SQLite stays the default. Chain construction and verification were extracted into shared functions so both backends produce identical records. PostgreSQL enforces append-only with row and TRUNCATE triggers, serialises appends across processes with an advisory lock, and indexes lookups by request. Evidence: `tests/test_audit_backends.py` (one contract, both backends), a four-writer concurrency test, and the 943-trial evaluation reproduced on PostgreSQL (0 false allows, 0 false blocks; median 1.8 ms per decision against 0.9 ms on in-memory SQLite). Setup, role privileges and limits: docs/postgres.md.

The PostgreSQL tests skip unless `VETO_TEST_PG_DSN` is set; running them in GitHub Actions needs a `postgres` service added to `.github/workflows/ci.yml`, which is a guard-rail file and needs the humans' explicit OK (proposed change below). Until then they run locally only.

### D-026 Shared state across gateway processes (2026-10-11) — ACCEPTED
Several gateway processes on one database now behave as one gateway. The audit log is the single source of truth: each decision runs inside a database-wide lock (PostgreSQL advisory lock; a no-op for single-process SQLite), first applies the records other processes appended since its last look (`audit.since(seq)`, same code path as restart replay, now `_apply`), then decides and appends. Principals and API keys can live in the same PostgreSQL database, with `last_used` written at most every 30 s. If catching up fails the request errors and nothing executes (fail closed). Evidence: `tests/test_multi_gateway.py` runs two services on one store: containment, session taint and resets, cross-process approvals, global pending cap and expiry, volume limits, shared keys and revocation, and a four-thread race; a control run with the lock removed overspent the limit (6 of 5 allowed), so the test is able to fail. The 943-trial evaluation is unchanged on PostgreSQL (0 false allows, 0 false blocks).
Cost and limits (state in the thesis): decisions serialise, so more processes add availability, not throughput; sign-in lockout counters and the mock resource's state stay per process; there is no database failover; observation id allocation can collide and is refused with 409. The multi-process tests for PostgreSQL run locally until the CI service change proposed in D-025 is approved (they pass for SQLite in CI).

### D-027 Multi-tenancy (2026-10-11) — ACCEPTED
Approved by Mohamed (model, new invariant, platform-admin access). One deployment serves many tenants with shared tables, a separate hash chain per tenant and, on PostgreSQL, row-level security. Decisions: (1) **Invariant 8 added** to CLAUDE.md and enforced statically in `scripts/check_invariants.py` (every SQL string on the audit table must filter by tenant, no audit method may take a tenant argument, the app may pick a tenant only from the authenticated principal). (2) The tenant comes only from the API key; principals are keyed `(tenant, id)`; headers, query strings and body fields naming a tenant are ignored. (3) Each tenant has its own `GatewayService` (policy, provenance, limits, approvals, kill switch) created on demand from the policy stored with the tenant; invalid policies are refused at creation. (4) Audit log objects are bound to one tenant, sequence numbers and the advisory lock are per tenant (tenants no longer wait for each other), and the tenant is sealed inside every record's hashed body so a moved row fails verification. (5) Platform layer: `platform_admin` creates, suspends and resumes tenants and has a global kill switch that tenants cannot release; it cannot act inside a tenant and sees counts and health only (as recommended, not decision content). Its actions form their own hash chain (`_platform`). (6) Sign-in failure and lockout counters are platform-level; tenants see only their own throttled-request count. (7) Rate limits are per `(tenant, principal)`. (8) Databases from before this entry migrate automatically: old audit rows and principals become the tenant `default`.
Evidence: `tests/test_tenancy.py` (35 SQLite+PostgreSQL cases and a row-level-security test): cross-tenant reads, approvals, spoofed tenant names, same agent ids, key and principal administration, observation id reuse and taint, per-tenant and platform kill switches, suspension, platform separation, per-tenant policy, flooding, independent and tamper-detecting chains, moved rows, legacy migration. A mutation check broke isolation in seven places one at a time (ignored tenant filters on reads and key revocation, rate key without tenant, no tenant binding in verify, platform kill ignored, suspension ignored) and every break failed a test; the invariant guard caught three deliberate violations. The evaluation (D-024) gains an isolation attack class (tenant beta against tenant alpha on a shared database: approve, read, scan, chain view) inside the zero-false-allow gate; a deliberate leak made `run_eval.py` exit 1. Results unchanged: 100% UIR, 0 false allows, 0 false blocks; median decision time about 1.1 ms (was 0.9) on in-memory SQLite.
Limits (state in the thesis): one process serves all tenants, so a bug in shared code is not contained by the data layer and one tenant can use more memory than another; row-level security does not bind a database superuser or table owner; principals, keys and tenants are protected by application checks and tests, not row-level security; no eviction of idle tenant runtimes; no policy editing after creation, per-tenant resource credentials, or tenant deletion or export. Containers or processes per tenant are the next isolation level.

### D-028 Audited policy editing (2026-10-11) — ACCEPTED
A tenant admin can change the tenant's policy while running; before this a policy was fixed when the tenant was created. Design: (1) **Propose, then a different admin activates.** `POST /v1/policy/proposals` lints the text, stores it with a machine diff (`loosens` is true when it adds an allow rule, removes a deny or approval rule, weakens an effect, or changes limits, agents, bands or provenance) and audits `POLICY_PROPOSED`. A proposal changes nothing. `.../{v}/activate` needs the `admin` role and an admin who is not the proposer (403 otherwise); a decided version is final (409). `.../{v}/reject` is audited. (2) **Lint as a hard gate** (`policy/lint.py`, run for every policy load, including the shipped one and the first tenant policy): required sections; unique ids and priorities; a reason on every rule; `default_effect` deny; the lowest-priority-number rule must be exactly `containment == true -> deny` (the kill switch can never be outranked or removed); no allow rule may key off an untrusted origin (invariant 4 cannot be edited away); no unconditional allow; 64,000 character limit; then the closed grammar (invariant 7). (3) **The chain carries the policy.** Activation writes `POLICY_ACTIVATED` with the full text and its SHA-256 before the new policy is installed; other gateway processes and restart replay apply it from the chain, so every decision's `policy_version` (id, version, content hash) can be tied to text in the evidence log. If the text does not match its recorded hash or fails the lint, the gateway forces containment and reports `policy.fault` in `/v1/state` and `/v1/policy` (fail closed; invariant 6). (4) Tenant-scoped like everything else: proposals are keyed by tenant, and the platform administrator cannot read or change a tenant's policy. Resolves policy-format Q2 (hot reload): through the audited path only, no file watching.
Evidence: `tests/test_policy_admin.py` (SQLite and PostgreSQL): the full workflow, proposer cannot activate, chain contents, reject, supersede, six lint rejections (none stored), malformed and oversized input, roles, tenant isolation, pickup by a second process, restart, a forged activation forcing containment, and the diff.
Limits (state in the thesis): the two-person rule stops one account from approving its own change, not two colluding admins (insider with full admin rights is out of scope, threat model section 8). Activation writes the chain first and the version table second; a crash between them leaves the chain (which wins at restart) ahead of the table, and activating again repairs it. Two admins activating different versions at the same moment can leave the table and the chain disagreeing about which is active; the chain is authoritative. Policy replay against recorded traffic (a what-if before activating) is not built.

### D-029 Webhook adapter for no-code tools (2026-10-11) — ACCEPTED
Zapier, Make and n8n-style automations can now call VETO without writing a client. A tenant admin defines a **hook** (`PUT /v1/admin/hooks/{name}`): which agent principal it acts as, which catalog verb it proposes, and how payload fields fill the target and parameters (`{field}` or `{a.b}` placeholders; the language is closed, no expressions, invariant 7). The automation calls `POST /v1/hooks/{name}` with that agent's API key and any JSON body (32 KB max) and gets a flat answer a Zap filter can branch on: `decision`, `status`, `executed`, `pending_approval`, `blocked`, `reason`, `request_id`, `effective_provenance`.
**A hook adds convenience, never authority.** (1) The call runs the normal pipeline (schema, catalog, taint, risk, deterministic policy, audit before execution, Execution Gateway). (2) The relayed content is registered as an observation by VETO and cited by the action; it can never be trusted. A hook may declare only an untrusted source (`unknown`, `email`, `web`, `external_document`, `sensor_ocr`, `model_generated`); `trusted_store`, `operator_input` and anything else is refused at definition time. (3) Because the observation is registered by the agent, session taint (T14) applies to that agent's later actions as well. Practical consequence, by design: a hook can read, or do things the policy allows from tainted contexts, but cannot unlock a door, change a clearance or send an external message on the strength of what the automation relayed; those are blocked or held exactly as for any agent. (4) Identity comes from the key: only the hook's own agent can call it (anyone else gets 404, so hooks do not leak), humans cannot, and tenants never see each other's hooks. (5) Optional `Idempotency-Key` header: a retry with the same key returns the first call's result (`replayed: true`) and writes nothing new; a failed call releases its key. (6) Definition changes (`HOOK_SET`, `HOOK_DELETED`) are audited with a hash of the definition; each call's observation and decision are in the chain as usual.
Evidence: `tests/test_hooks.py` (SQLite and PostgreSQL): the happy path with provenance, numeric placeholders, lies in the payload cannot unlock or send, session taint, containment, 11 bad definitions refused and not stored, roles, audit of changes, missing fields rejected before anything is registered, key/agent binding, oversized payloads, idempotency, tenant isolation, and the closed template language. Two deliberate breaks (hook callable by any agent; `trusted_store` accepted as a source) each failed a test.
Limits (state in the thesis): this is inbound only. The Execution Gateway still executes against the built-in mock resource; real connectors that call a customer's system (an outbound adapter holding that system's credentials, with SSRF protection and per-tenant credential storage) are the next step, and until then a Zap that receives `executed: true` has not changed anything in its own systems. A Zap that ignores `blocked` and acts anyway is outside VETO's reach: enforcement needs the outbound adapter or the MCP proxy (D-008). Notifying a Zap when a held action is approved needs outbound calls and is not built; poll `GET /v1/actions/{request_id}`. Idempotency keys are kept without expiry. No per-hook rate limit beyond the per-principal one.

### D-030 Outbound connectors (2026-10-12) — ACCEPTED
Until now an "executed" action changed only the built-in mock. A tenant can now route verbs to its own system through a **signed HTTPS webhook**, called by the Execution Gateway after the decision is audited. This is what makes invariant 5 real for a customer: VETO holds the credential and the automation tool never does.
**Model.** `PUT /v1/admin/connectors/{name}` `{url, verbs[], headers?, timeout_s?, enabled?, rotate_secret?}` (admin). The first definition returns a signing secret once. A verb with an enabled connector is sent there; any other verb still goes to the mock (so a tenant that wants nothing to run unconfigured should leave those verbs denied by policy). `GET` lists metadata (host, verbs, fingerprint, never the URL or secrets), `DELETE` removes, `POST .../ping` sends a signed `veto.ping` that executes nothing. Every change is audited (`CONNECTOR_SET`, `CONNECTOR_DELETED`, `CONNECTOR_PING`) with the host and a fingerprint of the secret, never the URL.
**The call.** `POST` of `{type: "veto.action", request_id, tenant, decision ("allow" or "approved"), action_hash, action{agent_id, action, target, parameters}, issued_at}` with `X-VETO-Signature: t=<unix>,v1=<HMAC-SHA256(secret, "<t>." + body)>`, `X-VETO-Request-Id`, `X-VETO-Action-Hash` and `Idempotency-Key: <request_id>`. The receiver verifies the signature, rejects a stale `t`, recomputes `action_hash` over `action` (same canonical form as the audit chain) and deduplicates on the request id. The Execution Gateway still refuses unless containment is off, the decision token verifies and the action hashes to the audited value, before any connector is opened; blocked, held, rejected and expired requests never reach it. 2xx is `executed` (optional `{"summary": "..."}` in the reply is shown), anything else is `failed`; a timeout after sending is reported as outcome unknown. Verification is `skipped` (VETO cannot inspect the other system), so status is `executed_unverified`. Three counted failures in a row (network errors, 5xx) pause that connector for 30 s so a dead endpoint cannot stall the tenant, because execution runs inside the decision lock.
**Secrets.** URL (webhook URLs are often secrets), custom headers (at most 3) and the signing secret are sealed with AES-256-GCM under a key from `VETO_SECRET_KEY` (at least 32 random characters, derived with HKDF), with `tenant|name` as associated data, so a blob copied to another tenant or name does not open. Without the key connectors are unavailable (503): fail closed. Only `veto/execution/` opens a sealed blob (a test scans the source tree). The API never returns secrets after creation.
**SSRF** (`execution/netguard.py`), checked at definition and again at every call: https only, no credentials in the URL, port 443 or 8443, every resolved address must be globally routable (so loopback, private, link-local and cloud-metadata ranges, carrier-grade NAT, and IPv4-mapped forms are refused), connection pinned to the vetted address with the certificate checked against the original host name, no redirects, timeout of at most 10 s, response read capped at 64 KB, reserved headers refused.
Evidence: `tests/test_connectors.py` (41 cases incl. a real TLS round trip to a local server): signature and hash binding, held-then-approved, blocked/contained/rejected never sent, forged token and changed action refused, failures and pause, routing and fallback, 24 unsafe definitions refused, DNS that changes after the check, secrets never in responses, audit or state, roles, missing key, wrong key, tenant isolation (including a sealed blob moved across tenants), source-tree scan. Five deliberate breaks (no public-address check, no associated data, no hash check, no containment check, extra port) each failed a test; one survived the first time (no test hit the gateway's containment check with a valid token), so that test was added.
Limits (state in the thesis): the receiver must verify the signature; a connector endpoint that does not is trusting anyone who finds its URL. Execution is synchronous inside the tenant's decision lock (bounded by the timeout and the pause), so a slow endpoint slows that tenant's decisions; an asynchronous queue is future work. Delivery is at-most-once from VETO's side (no automatic retry, because an unknown outcome could duplicate an irreversible action); the idempotency key lets a receiver make a manual retry safe. One signing secret per connector, no per-verb credentials, no mutual TLS, no allow-list of destination hosts per tenant. A tenant admin alone can point a connector anywhere public, which is the same trust as editing the policy without the second-person rule; platform-level host allow-lists would close that. The master key lives in the environment, not in a KMS; rotating it means re-sealing every connector. Unrouted verbs still reach the mock. Connector tests need the `cryptography` package; until it is added to the CI workflow they are skipped in GitHub Actions (they run in `scripts/ci.sh`).

### D-031 External timestamping of the audit chain (2026-10-12) — ACCEPTED
**Problem.** The hash chain (invariant 6) detects edits unless the editor recomputes every later hash. Someone with write access to the database (the one attacker the chain alone cannot stop) can do exactly that, and the result still verifies. Truncation from the end is also invisible to the chain.
**Decision.** Periodically send each chain's head to an independent RFC 3161 time-stamp authority and store the signed receipt. The timestamped value is `SHA-256("veto-anchor-v1|<tenant>|<seq>|<record_hash>")`, so a receipt is bound to one tenant and one position. `GET /v1/anchors/verify` compares every receipt with the log: a rewritten log cannot reproduce the timestamped hash, and a log shorter than an anchor shows removal. Per tenant, plus the `_platform` chain. Configuration (operator): `VETO_TSA_URL` (https or http; the reply is self-authenticating), `VETO_TSA_CA` (PEM chain of the authority; when set, every reply's signature is verified with `openssl ts -verify` before it is stored), `VETO_ANCHOR_INTERVAL_S` (default 3600; `0` disables the background loop). Admins can anchor at once (`POST /v1/anchors`); any human role can list, verify and download a receipt (`/v1/anchors`, `/v1/anchors/verify`, `/v1/anchors/{seq}/receipt`). `scripts/verify_receipt.py` lets an auditor check a receipt and an exported log on their own machine without trusting the VETO server.
**Rules.** (1) Never cement a broken chain: before anchoring VETO verifies the records added since the last anchor against that anchor's head (the whole log the first time) and refuses if they do not link. (2) A reply is stored only if it is granted, covers our digest, echoes our nonce, and (with a CA configured) carries a valid signature; anything else is reported and the next attempt retries. (3) Anchors are not themselves written to the chain (that would move the head and anchor forever); they are tenant-keyed rows, and creating one by hand is not an audit event. (4) Failure to reach the authority never affects a decision: timestamping is evidence, not a gate. (5) The authority is chosen by the deployment operator, not by tenants. Calls go through the same address-pinned, public-addresses-only client as connectors (http allowed on ports 80 and 8080 for authorities that only offer it).
**Evidence.** `tests/test_anchoring.py` runs a real RFC 3161 authority built with OpenSSL: request/reply round trip with signature check, digest binding, storage and receipt, skip-when-unchanged, a perfectly rewritten chain that the hash chain accepts but the timestamp rejects, truncation, five misbehaving authorities (HTTP 500, garbage, refusal, token for another digest, wrong nonce), a reply signed by the wrong authority, refusal to anchor a broken chain, roles and tenant isolation, platform chain, background loop, auditor script. Six deliberate breaks (no log comparison, no nonce check, no digest check, no signature check, no chain check, no shortness check) each failed a test; the digest check first survived because the signature check masked it, so a test without a CA was added.
**Limits (state in the thesis).** Not tested against a public authority (this build environment has no general internet). A receipt proves the chain head existed by the authority's stated time; it does not prove the records were true when written, and nothing written after the last anchor is covered (up to one interval of exposure; shorten the interval or anchor on demand for high-stakes moments). The local authority used in tests and the guided tour is untrustworthy by design. A free authority is fine for a demo or thesis; for evidence with legal weight use a qualified commercial authority and keep its certificate chain safe. The verifier requires `openssl`. If the authority's certificate expires or is revoked, old receipts need that chain's own long-term validation story, which is not built.
